# 이미지 호스팅·소개 사이트·배너 제작

크랙 작품의 외부 이미지 주소, 공개 소개 사이트, 클릭형 배너를 함께 설계할 때 읽는다. 상세설명·댓글 원고는 [derived-assets-and-showcase.md](derived-assets-and-showcase.md), 이미지 생성은 [image-prompt-and-assets.md](image-prompt-and-assets.md)를 따른다. 이미지 없이도 텍스트 플레이가 성립해야 한다.

## 1. 공개 범위와 파일 계약

먼저 정본에서 작품명, 시작 상황·신분, 초반에 필요한 공개 인물 소개, 실제 지원하는 명령어를 추린다. 사이트에는 광고성 후크나 카피를 추가하지 않는다. 반전·숨겨진 관계·엔딩 조건은 사이트 데이터와 HTML 메타 태그에도 넣지 않는다. 이미지 제작 계획과 실제 공개 수량을 구분한다.

권장 작업 구조(플랫폼 강제 규격이 아닌 프로젝트 관례):

```text
<project>/
  build/assets/
    prompts.json                  # 기존 이미지 축·슬러그 정본
    showcase-brief.md              # 공개 문구, 화면 구성, 배너 제목·구도
    release-check.md               # 공개 URL, 실제 수량, 검증 결과
  image-originals/                 # 원본 보관, 공개 대상 아님
  image-staging/                  # 런타임 CG만 변환·검사하는 작업 사본
  site/                           # 소개 사이트의 공개 파일만
    index.html
    styles.css
    app.js
    banner.webp
    thumbnail.webp
    cg/                           # 검증한 image-staging 내용 복사
      <character-slug>/<code>.webp
      scene/<code>.webp
      bg/<code>.webp
      mob/<code>.webp
      event/<code>.webp
```

사이트 URL과 이미지 기준 URL은 별도로 기록한다. 위 구조라면 각각 `https://<host>/`와 `https://<host>/cg`다. 하위 경로 배포 시 그 접두사까지 포함한다. 원본·프롬프트·비밀 설정·작업 메모를 공개 폴더에 복사하지 않는다.

**번호는 기존 프로젝트 계약을 보존한다.** 현재 예제는 `seorin/a01.webp`처럼 영문 인물 슬러그와 일반 이미지 `a` 코드를 사용하지만, 참고 저장소에는 `s=safe, a=adult` 관례도 있다. 접두사만 보고 등급을 추정하거나 숫자 ID로 일괄 변경하지 않는다. `prompts.json`의 키, 실제 파일, 프롬프트 호출, 갤러리 URL을 일치시킨다. 새 프로젝트는 선택한 코드와 등급 의미를 배치표에 명시한다.

## 2. 로컬 준비와 기존 도구의 실제 범위

도구는 스킬 루트 `$S/tools/images/`에 있다. 아래 `$P`는 작품 경로다. 모든 호출에 해당 작품의 `--config`를 명시한다.

```bash
S="<스킬 루트>"
P="<작품 경로>"
python3 "$S/tools/images/deploy.py" --help
python3 "$S/tools/images/deploy.py" --check --config "$P/build/assets/prompts.json" --root "$P/image-staging"
```

- **WebP 변환**: `--convert-webp`는 변환에 성공한 PNG/JPEG를 삭제하고 같은 이름의 WebP를 덮어쓸 수 있다. 원본을 보존한 뒤 작업 사본에서만 실행한다. 압축률·로딩 속도를 고정 수치로 약속하지 말고 결과의 용량과 시각 품질을 확인한다.
- **스캐폴드**: `--scaffold`는 폴더·배치표·웹 템플릿을 만든다. HTML/CSS/JS를 덮어쓰므로 새 임시 폴더에서 실행한다. 일부 표 생성은 문자열 대신 `{"ko":"표시명"}` 형태의 값을 기대한다. 입력을 확인하고 필요하면 작업용 설정 사본을 사용한다.
- **템플릿 한계**: 현재 생성기는 폴더에 실제 슬러그를 쓰면서 웹 데이터에는 순번 ID와 `/01/a01.webp`를 만들고, 소속과 등급에도 샘플 가정을 사용한다. 생성 후 실제 슬러그·대표 이미지·소속·등급으로 수정하고 데모 인물과 문구를 제거한다. 생성 성공을 소개 사이트 완성으로 보고하지 않는다.
- **검사 한계**: `--check`는 예상 밖 WebP와 과대 파일 등을 검사하지만 일부 조합 누락은 실패로 처리하지 않는다. 공개 목록의 파일 존재·디코딩·링크를 별도로 검사한다. `banner.webp`와 `thumbnail.webp`는 런타임 축이 아니므로 CG 검사 루트 밖에 둔다.
- **배포 한계**: `deploy.py`의 기본 실행은 Cloudflare Pages 배포가 아니라 GitHub+jsDelivr 이미지 배포다. 기존 WebP 삭제·강제 푸시를 수행하며 사이트 HTML/CSS/JS는 함께 올리지 않는다. `--dry-run`도 인증 조회와 `.deploy-work` 정리를 수행하므로 순수 로컬 검사로 취급하지 않는다. 사이트 배포용으로 무인 실행하지 않는다.

## 3. 소개 사이트 구성과 문구

먼저 [작품 연장형 사이트 설계](immersive-showcase-design.md)를 읽고 작성자·시점·열람 권한·공개 정보 장부를 정한다. 소개 사이트는 작품 안의 기록·공고·단말기 경험으로 설계한다. 아래는 수록 내용의 역할이며 고정 섹션 순서가 아니다. 선택한 형식에 맞춰 문서 트리·게시판·연대기로 배치한다.

기존 `tools/images/web_template/`는 갤러리 출발점이다. 작품 분위기에 맞춰 색·서체·구도를 정하고 아래 읽기 흐름으로 구성한다. 어두운 테마나 네 개 탭을 모든 작품에 강제하지 않는다.

| 영역 | 작성 내용 | 완료 기준 |
|---|---|---|
| 첫 화면 | 작품명 또는 기록명, 시작 상황, 대표 비주얼(선택), 실제 작품 링크 | 모바일 첫 화면에서 어떤 역할을 즐기는지 이해됨 |
| 세계와 플레이 | 공개 배경 2~3문장, 플레이어 역할, 주로 하게 될 선택 | 설정집 대신 플레이 경험을 설명함 |
| 인물 도감 | 이름·공개 소속·역할·첫인상, 짧은 대표 대사, 대표 이미지 | 숨은 욕망·공략 정답·내부 심리 슬롯은 노출하지 않음 |
| 갤러리 | 실제 존재하는 인물·장소·이벤트 이미지, 필요한 필터와 확대 보기 | 비어 있는 조합을 버튼으로 만들지 않음 |
| 시작 안내 | 첫 입력 예, 등록된 단축어, 작품 등급·콘텐츠 안내 | 실제 시작 세트·키워드북과 일치함 |
| 마지막 안내 | 플레이 링크, 제작자 문구, 제공된 경우 업데이트 정보 | 가짜 URL·연락처·기능 약속이 없음 |

갤러리 데이터에는 표시 이름과 파일 슬러그를 분리하고, 각 변형의 실제 경로·표시명·공개 등급을 기록한다. 인물별 장수가 다르면 전체 상황 축의 곱으로 만들지 않는다. 공개 사이트에 성인 자료를 포함할지는 요청 범위와 배포 서비스 규칙에 맞춘다. 단순 19+ 토글은 직접 이미지 URL의 접근 제한이 아니다.

모바일 360~390px와 데스크톱에서 가로 넘침·잘린 문구·깨진 이미지를 확인한다. 호버에만 정보를 숨기지 말고 터치로도 열리게 한다. 확대 창은 닫기 버튼·Esc·키보드 초점 복귀를 지원한다. 첫 화면 이미지는 우선 로드하고 아래 갤러리는 지연 로드하며, 이미지 크기를 지정해 레이아웃 이동을 줄인다. 공유용 제목·설명·썸네일도 공개 문구와 일치시킨다.

## 4. 배너 제목·구도·제작

배너는 작품 또는 기록의 표지로 설계한다. 홍보성 카피를 추가하지 않고 작품의 분위기와 정체성을 전달한다. `showcase-brief.md`에 다음을 작성한다.

- 사용 위치: 크랙 상세설명 상단 / 사이트 히어로 / 공유 썸네일.
- 문구: 작품명 또는 기록명. 클릭 기능 설명이 꼭 필요하면 ‘기록 열기’ 정도로 쓴다. 과장된 후크·캐치프레이즈·기능 홍보를 넣지 않는다.
- 구도: 주인공 또는 상징물 하나를 중심에 두고 문구 영역을 비운다. 모바일 크롭에서 얼굴·제목이 함께 살아남도록 핵심 요소를 가장자리에서 떼어 둔다.
- 시각 명세: 작품 색상 2~3개, 배경 밝기, 글자 대비, 인물 시선, 초점 위치, 목표 비율과 출력 파일명.

가로 배너 `1600×600`, 공유 썸네일 `1200×630`은 작업 시작값이며 크랙의 강제 규격이 아니다. 실제 사용 위치의 표시 비율에 맞춰 조정한다. 한 이미지를 무리하게 늘이지 말고 용도별 크롭을 만든다. 배너 안 한글이 잘못 생성되면 정확한 문구를 별도 타이포그래피 레이어로 조판하고 축소본에서 읽히는지 확인한다. 이미지 생성·편집은 사용 가능한 이미지 도구 지침을 따른다.

크랙 상세설명에는 CSS나 스크립트 대신 링크를 감싼 이미지를 쓴다:

```markdown
[![작품명 — 인물과 일러스트 둘러보기](https://<host>/banner.webp)](https://<host>/)
```

배너 클릭 대상은 소개 페이지이고 이미지 주소는 이미지 파일이다. 주소 미정이면 초안에만 표시하고 등록용 최종본에 가짜 주소를 남기지 않는다. 배너가 없으면 텍스트 소개 링크로 대체한다.

## 5. 호스팅과 연결 검증

기존 호스팅과 사용자가 지정한 서비스를 우선한다. Cloudflare Pages는 이 저장소의 참고 배포 방식이다. 실제 배포 시 해당 서비스의 공식 문서와 사용 가능한 배포 도구에서 현재 절차·용량 제한을 확인한다. 무료·무제한·즉시 갱신을 보장하지 않는다. Sites로 제작하는 요청은 사용 가능한 Sites 스킬의 제작·호스팅 흐름을 따른다.

1. 공개할 파일만 `site/`에 조립하고 로컬 미리보기에서 레이아웃·필터·확대·플레이 링크를 확인한다.
2. 배포가 요청 범위에 포함되어 있으면 해당 호스팅 절차로 정적 사이트 전체를 배포한다. 문서 보강이나 로컬 제작 요청만으로 외부 공개를 추가하지 않는다.
3. 배포 결과의 실제 HTTPS 주소를 확인한다. 루트 페이지뿐 아니라 배너·썸네일·갤러리와 런타임 CG의 모든 참조 URL을 검사한다. 응답이 성공해도 HTML 오류 페이지일 수 있으므로 이미지 Content-Type과 실제 표시도 확인한다.
4. 배너→소개 사이트→작품 플레이 이동을 확인한다. 사이트 주소와 CG 기준 주소를 상세설명·갤러리·통합 프롬프트에 일관되게 반영한다. 크랙 등록이 요청 범위 밖이거나 화면을 확인할 수 없으면 해당 검증을 미확인으로 기록한다.
5. 이미지 교체 시 버전 경로 또는 일관된 revision 쿼리로 참조를 갱신하고 구버전 호출이 남는지 확인한다. 프롬프트에서 쓰는 공개 경로를 임의로 삭제하지 않는다.

`release-check.md`에는 사이트/배너/CG/작품 URL, 실제 공개 파일 수와 집계 기준, 확인한 화면 크기, 깨진 링크 결과, 미확인 항목을 기록한다. 로컬 완성·배포 완료·크랙 등록 완료를 구분해 보고한다.
