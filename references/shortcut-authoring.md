# 단축어 작성 지침

크랙 단축어는 한 번 호출해 **이번 응답의 동작**을 바꾸는 명령이다. 작품의 정본과 통합 프롬프트를 대신하지 않는다. 등록 형식과 글자 수 제한은 [플랫폼 규격](platform-spec-and-lint.md) 및 [키워드북 등록 규약](keyword-book-guide.md)을 따른다. 아래 유형은 사용자가 제공한 단축어 사례에서 뽑은 **설계 패턴**이며, 예시 문장을 그대로 등록하라는 뜻이 아니다.

## 1. 먼저 결정할 여섯 가지

| 결정 | 작성할 내용 |
|---|---|
| 호출 | `이름`으로 등록하고 프롬프트에는 `/이름 [인자]`의 인자 해석을 적는다. 버튼 호출에 인자가 없을 때의 기본값도 정한다. |
| 범위 | 이번 응답만 적용할지, 사용자가 재개할 때까지 OOC 상태를 유지할지 정한다. 단축어 한 번으로 시스템 프롬프트를 영구 수정한다고 주장하지 않는다. |
| RP | 중단 후 정보만 출력, 직전 응답 교정, 장면 계속, 시간 이동 중 하나를 명시한다. |
| 입력 근거 | 최근 대화, 장기기억, 정본, 유저노트 중 무엇을 참고할지와 우선순위를 적는다. 실제로 볼 수 없는 로그·날짜·이미지는 생성하지 않는다. |
| 출력 | 코드블록 여부, 항목 수, 길이, 말미의 상태창 포함 여부, 마지막 장면의 멈춤 지점을 정한다. |
| 다음 턴 | RP 자동 복귀인지, 사용자 지시까지 대기인지, 메타 출력이 캐릭터 기억에 들어가지 않는지 명시한다. |

**권장 작성 순서:** 호출 조건 → 이번 응답의 모드 → 참조 범위 → 실행 규칙 → 출력 형식 → 다음 턴 처리. 400자 안에 안 들어가면 장식적인 금지 문구와 중복 예시부터 줄인다. 기능이 여러 개인 OOC는 서로 다른 명령으로 분리하거나 인자별 분기를 짧게 적는다.

## 2. 공통 안전장치

- **PC 주권:** 단축어로 시간·사건을 건너뛰거나 응답을 고쳐도 `{user}`의 대사·생각·감정·선택·행동을 새로 확정하지 않는다. 이미 입력한 행동도 불필요하게 다시 출력하지 않는다. 마지막은 유저가 개입할 수 있게 둔다.
- **사실과 추정 분리:** 요약·상태점검·OOC 진단은 대화에서 확인된 사실을 우선한다. 빠진 구간을 메우거나 인물의 속마음을 단정하려면 작품 설정상 그 정보가 허용되는지 확인한다. 원인을 확인할 수 없는 모델 오류는 기술적 원인인 양 단정하지 않는다.
- **캐릭터 인지 경계:** OOC, 요약, SNS·커뮤니티의 관찰자 화면은 캐릭터가 본 사건이 아니다. 이후 RP에서 캐릭터가 이를 안 것처럼 반응하지 않게 한다. 반대로 실제 장면에서 발생한 사건과 시간 경과는 인물이 인지할 수 있다.
- **출력 계약:** `코드블록만`, `본문만`, `상태창 포함`, `설명 금지`처럼 결과를 검증할 수 있게 쓴다. 코드블록 안에 다시 코드펜스를 넣는 중첩 형식은 피하고, 펜스 언어와 본문만 지정한다.
- **분량과 재화:** 1회 호출의 목적을 정하고 출력 목표는 플랫폼에서 가능한 길이로 잡는다. 무조건 3,600자·이미지 여러 장을 강제하지 않는다. 이미지가 없다면 이미지 출력을 약속하지 않는다. 반복 HUD나 이미 보이는 상태창의 재출력은 필요성을 따진다.
- **등급·인물 설정:** 성인 장면 관련 명령은 해당 작품의 등급, 성인 인물 설정, 현재까지 성립한 의사를 따른다. 시간 이동으로 동의·관계 진전·결과를 임의 확정하지 않는다. 전연령판과 성인판의 동작이 다르면 각각 명시한다.

## 3. 유형별 설계

| 유형 | 호출 시 동작 | 빠뜨리기 쉬운 계약 |
|---|---|---|
| 장기기억 요약 | RP 중단, 보이는 최근 대화만 날짜순으로 압축 | 날짜·시각이 없으면 추정하지 않음. 사건, 끝난 목표, 관계 변화, 다음 목표를 구분. 항목당 목표 글자 수와 출력 펜스 지정. |
| OOC 질문 | RP 중단, 메타 질문에 중립적으로 답변 | 답변 후 자동 복귀/대기 중 하나. 캐릭터 비인지. |
| OOC 오류 교정 | 직전 오류를 바로잡거나 원인·조치를 보고 | **교정 재출력**과 **진단 보고**는 다른 결과. 원인 추측을 사실처럼 쓰지 않음. |
| 연속 출력 | 직전 마지막 문장에서 장면을 이어감 | 직전 상황 에코 금지, PC 대필 금지, 개입 지점에서 정지, 본문 외 보고 금지. 이미 닫힌 장면이면 억지로 연장하지 않음. |
| 장면 생략 | 직접 묘사를 건너뛰고 이후 장면에서 재개 | `/밤스킵`처럼 **과정 생략**인지, 경과 사건을 **회상 서술**할지 분명히 한다. 두 동작을 같은 명령에 섞지 않음. |
| 시간·사건 스킵 | `/스킵`, `/스킵 <시간>`, `/스킵 <사건>`을 구분 | 목적 시점, 건너뛴 사실의 서술 깊이, 계승할 상태, 유저가 결정해야 할 사건에서 멈출 조건. |
| 사건 발생 | 현재 갈등에서 사건 하나를 발생시키고 인물 반응까지 출력 | 무작위 위기·기존 갈등의 임의 종결 금지. 사건 이후 PC 선택 여백. |
| 외부 화면 | 커뮤니티·SNS 등 형식화된 가상 게시물 출력 | 게시물·댓글 수, 화자, 시간, 말투, 코드블록 여부. 제3자의 소문과 실제 사실을 구별하고 캐릭터 비인지 처리. |
| 사칭 교정 | 문제 턴을 PC 주권에 맞춰 다시 출력 | 무엇을 무효화할지, 수정본의 범위, 다음 턴 여백. 오답노트 HUD가 필요하면 짧고 정확하게; 불필요하면 생략. |
| 엔딩 | 누적 선택을 근거로 결말과 에필로그 작성 | 사용자가 엔딩을 명시적으로 요청했는지, 미해결 갈등의 처리 범위, 주·조연의 후일담. PC의 이후 삶을 마음대로 확정하지 않도록 정본의 선택권 규칙 확인. |

### 특히 구분할 쌍

- **요약 vs 장기기억:** `요약`은 당장 상황 파악용 짧은 브리핑이고, `장기기억`은 날짜별 사건·관계·예정 목표를 다음 문맥에 넘기기 위한 기록이다. 최근 30턴을 요구해도 실제로 전달된 대화 범위만 사용한다.
- **OOC 대기 vs 자동 복귀:** 사용자 제공 사례의 OOC는 “동의할 때까지 대기”와 “다음 턴 RP 복귀”가 섞여 있다. 작품별로 하나를 선택하고 통합 프롬프트의 `/OOC` 규약과 맞춘다.
- **밤스킵 vs 과정 서술형 스킵:** 전자는 직접 묘사를 건너뛰는 페이드아웃이다. 후자는 경과를 서술하므로 ‘스킵’이라는 이름만으로 결과를 알 수 없다. 사용자에게 보이는 설명에 차이를 적는다. 성적 행위의 횟수나 이미지를 기계적으로 강제하지 않는다.
- **실제 게시물 vs 가상 게시물:** 커뮤니티·SNS 단축어의 출력은 작품 속 가상 화면이다. 실제 서비스에 게시하거나 실제 사용자의 반응을 조회한다고 쓰지 않는다.

## 4. 400자 컴파일 틀

다음은 구조를 보여 주는 **작성 틀**이다. 중괄호 내용은 작품에 맞춰 교체하고, 완성본은 UTF-16 길이 검사를 거친다.

```text
/{명령} [인자]: {인자별 동작·기본값}. 이번 응답은 {RP 중단/교정/진행}.
근거: {참조 범위}; 확인되지 않은 사실은 만들지 않는다.
실행: {핵심 1~2개}; {user}의 대사·행동·선택을 대신 쓰지 않는다.
출력: {형식·분량·종료 지점}. 다음 턴: {자동 복귀/재개 지시 대기}; {캐릭터 인지 여부}.
```

예를 들어 장기기억이면 `최근 보이는 대화만`, `날짜순 사건·관계 변화·예정 목표`, `sum 코드블록만`, `다음 턴 RP 복귀`를 우선 남긴다. OOC 오류 진단이면 `오류/원인(확인·추정 구별)/수정`과 `재개 조건`을 남긴다. 시간 스킵이면 `목적 시점/계승 상태/PC 선택 대기`를 남긴다. 예시의 여러 줄 출력 틀과 이스케이프 기호(`\#`, `\-`, `&#x20;`)는 등록 프롬프트에 그대로 넣지 말고 실제 문장으로 정리한다.

## 5. 등록 전 점검

1. 통합 프롬프트의 OOC·상태창·PC 주권·등급 규칙과 충돌하지 않는가?
2. 버튼만 눌렀을 때 인자 없는 기본 동작이 명확한가? `/명령 <인자>`를 직접 입력했을 때도 같은 규칙이 적용되는가?
3. 한 번만 적용하는 명령과 재개 전까지 유지하는 명령이 구분되는가?
4. 출력 형식·근거 범위·캐릭터 인지 여부·다음 턴 동작을 확인할 수 있는가?
5. 이름·설명·프롬프트가 플랫폼 한도 안인가? 실제 등록명과 상세설명의 안내명이 같은가?

기술적 한도는 `scripts/checks/check_keyword_book.py`로 검사한다. 동작 품질은 서로 다른 상황(정상 호출, 인자 없음, 인자 있음, 정보 부족, PC 선택이 필요한 장면)에서 직접 확인한다.

## 6. 표준 단축어는 원문 그대로

OOC·요약·사칭교정·기록정리·마감형(다음날로/영업종료)은 [platform-spec-and-lint.md](platform-spec-and-lint.md) 레시피 문구를 **그대로** 쓴다. 작품에 맞춘다고 항목·분량을 바꾸면 작품마다 동작이 달라져 플레이어가 헷갈린다. 이름·날짜 단위처럼 꼭 필요한 낱말만 바꾼다. 작품 전용(상태점검·시장소문 등)만 새로 짠다.
